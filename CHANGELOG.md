# Changelog

All notable changes to StackBraid are documented here, following [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- Product specification, architecture, folder structure, roadmap and release checklist.
- Contributor and agent instructions.
- The `Identity` API contract (`contract/openapi.yaml`): auth, users and roles, validated against OpenAPI 3.1.
- A conformance suite (`contract/conformance/`), written against the contract and runnable against any backend on any database provider, with a stub fixture proving it catches contract violations.
- Generated TypeScript (`clients/typescript/`) and Dart (`clients/dart/`) clients, wired to regenerate from `contract/openapi.yaml` with one command (`scripts/generate-clients.sh`), plus a drift check and pre-commit hook that fail when the committed clients no longer match a fresh generation. Both clients have since called a real running .NET backend successfully, with no hand edits.
- The .NET backend's `Identity` feature (`backends/dotnet`): `Shared` cross-cutting plumbing (a provider-agnostic persistence base, the RFC 9457 Problem envelope, correlation IDs, rate limiting, localization in English and Spanish, password and refresh-token hashing, and one minimal working implementation each for messaging, jobs, documents, caching, storage and mailing); the Identity domain (`User`, `Role`, `RefreshToken`, five domain events, genuinely zero dependencies); a Postgres provider (migrations, idempotent seeding); the full Application layer (one command or query per contract operation); and the HTTP surface — JWT-authenticated, permission-gated minimal API endpoints. Proven against a real, throwaway local Postgres cluster (no Docker, no Testcontainers) and against `contract/conformance` itself: 34 of 34 checks pass. 115 unit and integration tests (32 + 65 + 18 across three test projects), all passing.
- The repository folder scaffold from `docs/STRUCTURE.md` — `frontends/`, `mobile/`, `create/`, and the Python half of `backends/` — each a placeholder stating plainly that no code lives there yet.
- `infra/compose.yaml`: Postgres, RabbitMQ, Redis, Prometheus, Loki and Grafana on one network, every value defaulted so the stack runs with no `.env` file. Prometheus scrapes itself and RabbitMQ's built-in metrics plugin; Grafana auto-provisions both datasources and three pre-built dashboards (`infra/grafana/dashboards/`). `.env.example` names every variable the compose file reads and fills none in.
- CI (`.github/workflows/ci.yml`): lint (shellcheck, yamllint, dashboard JSON validation), build (compose config validation, TypeScript client typecheck), test (the Dart client's test suite), and a `client-drift` job that runs `scripts/check-client-drift.sh` in CI so drifted clients can no longer reach `main` through an unconfigured clone or a `--no-verify` commit.
- A dependency licence audit (`docs/DEPENDENCIES.md`, `docs/dependency-inventory.json`): every npm dependency in `clients/typescript/`, every Dart dependency in `clients/dart/`, every Docker image in `infra/compose.yaml`, and both backends' own resolved dependency graphs, verified against actual package and licence metadata rather than carried forward from a prior note, with the date each entry was checked. All dependencies compiled into a consumer's code are MIT, Apache-2.0, BSD-2/3-Clause or PSF-2.0. No third-party code is vendored or redistributed today, so no `THIRD_PARTY_NOTICES` file is required — that determination is recorded in writing in `docs/DEPENDENCIES.md`. A CI job (`scripts/check-dependency-licenses.mjs`) now fails the build if a dependency is added, or changes version, without a matching audited entry.
- The Python backend's `Identity` feature (`backends/python`): `shared/` cross-cutting plumbing mirroring the .NET backend in Python idiom (FastAPI/SQLAlchemy, Protocol ports instead of interfaces) — a provider-agnostic persistence base, the RFC 9457 Problem envelope, correlation IDs, rate limiting, localization in English and Spanish, PBKDF2 password hashing and opaque refresh-token hashing, and one minimal working implementation each for messaging, jobs, documents, caching, storage and mailing; the Identity domain (`User`, `Role`, `RefreshToken`, five domain events, genuinely zero dependencies, enforced by `import-linter`); a Postgres provider (Alembic migrations, idempotent seeding); the full application layer (one command or query per contract operation, no mediator — handlers resolve directly from FastAPI's dependency graph); and the HTTP surface — JWT-authenticated, permission-gated FastAPI endpoints. Proven against a real, throwaway local Postgres cluster (no Docker, no Testcontainers) and against `contract/conformance` itself, unchanged from the .NET run: 34 of 34 checks pass. Both generated clients called this backend successfully with only their base URL changed. 40 unit and integration tests, all passing.

- The Next.js frontend's web and admin shells (`frontends/nextjs`): Clean Architecture across every feature (`domain/ application/ data/ presentation/`, enforced by `dependency-cruiser` — each rule seen to genuinely fail against a deliberate violation), consuming `clients/typescript` unchanged. `web/` — register, sign in, an httpOnly-refresh-cookie session that survives a reload, a read-only profile view (`GET /v1/auth/me`, the only self-service endpoint an ordinary account holds a permission for). `admin/` — a users list (search, status filter, pagination, deactivate), a user detail screen (assign/revoke roles), a roles catalogue, reachable only for an account holding the `admin` role and enforced by a client-side guard (a Next.js middleware/proxy file cannot do this job: the refresh cookie is scoped to the backend's own `/v1/auth` path and is never visible to this app's own server). shadcn/ui + Tailwind, TanStack Query, next-intl with English and Spanish shipped per feature. Both backends gained a CORS allow-list (`Cors:AllowedOrigins` / `STACKBRAID_CORS_ALLOWED_ORIGINS_RAW`, empty and inert by default) so a browser-based frontend can reach them at all. Proven against a real, throwaway local Postgres cluster and each backend's real server in turn, `NEXT_PUBLIC_API_BASE_URL` the only thing that changed: the same Playwright spec (register → survive a reload → admin unreachable without the role → sign out → sign back in → the seeded administrator assigns that role from the real screen → the real roles catalogue) passed against both, unchanged.
- The Playwright Identity-flow spec moved to a shared `e2e/identity-flow.ts`, used by both frontends through a three-line per-project wrapper (`frontends/*/e2e/identity-flow.spec.ts`) rather than kept as two copies — one script, proven against two frontends and two backends without ever changing.
- The Angular frontend's web and admin shells (`frontends/angular`): the same feature names and the same Clean Architecture layering as the Next.js app (`domain/ application/ data/ presentation/`, enforced by `dependency-cruiser` — every rule seen to genuinely fail against a deliberate violation, then reverted), consuming `clients/typescript` unchanged, idiomatic Angular throughout — standalone components, signals for all local and session state (no NgRx), the Router's own functional guards, Angular Material (MIT) with Tailwind for layout, and `@jsverse/transloco` with a scoped inline loader per feature so localized strings ship with the feature that owns them, exactly as `next-intl` does on the Next.js side. Same screens, same behaviour: register, sign in, a read-only profile; an admin area (users list with search/filter/pagination/deactivate, user detail with assign/revoke roles, a roles catalogue) reachable only for the `admin` role, gated by a route guard that awaits the httpOnly-refresh-cookie hydration before deciding — no server-side proxy problem to work around here, unlike Next.js. Proven with the same shared Playwright spec against both backends, `public/env.js` (a runtime-read file, not a build-time environment variable) the only thing that changed between runs — the same compiled build, repointed with no rebuild.
- **The four-run parity proof both frontend cards needed:** the one shared Playwright spec, run against Angular and Next.js, against both the .NET and the Python backend — four runs, changing only the frontend under test and the backend URL it was started against, all four green.
- The Flutter mobile shell's `Identity` feature (`mobile/flutter`): Clean Architecture for the one `auth` feature (`domain/ application/ data/ presentation/`), enforced by a hand-written `flutter test` boundary check (Dart has no dependency-cruiser/import-linter equivalent) — five rule shapes, each seen to genuinely fail against a deliberate violation, then reverted. Consumes `clients/dart` unchanged via a `path:` dependency. Register, sign in, a session persisted through platform secure storage (`flutter_secure_storage`, iOS/macOS Keychain and Android Keystore) that survives a fresh app instance, a profile screen, sign out and sign back in — the access token itself stays in-memory only, resolving `docs/SPEC.md`'s previously-open "mobile token storage" question. English and Spanish, each feature shipping its own translations. No admin surface, by design (`docs/STRUCTURE.md`: administration is a desktop job) — "list users, assign a role" is proven instead directly through the generated client, using the seeded administrator. A logging interceptor redacts every token, cookie and password field before anything is printed; a dedicated test feeds real secret values through it and asserts they never appear in the output. Proven with `integration_test/identity_flow_test.dart` against a real, throwaway local Postgres cluster and each backend's real server in turn, `--dart-define=API_BASE_URL` the only thing that changed — run on the macOS desktop target only (no iOS or Android simulator installed or downloaded for this work). 15 further unit tests (validation, use cases, log redaction) all passing.

Both backends' `Identity` feature is implemented and tested. Both the Next.js and Angular frontends' web and admin shells are implemented and verified against both backends, using the same Playwright script. The Flutter mobile shell's `Identity` feature is implemented and verified against both backends on the macOS desktop target only. Nothing else is. There is no release. The infrastructure stack has not been run end to end on a clean machine — see the commit messages above for exactly what was and was not verified.
